1. Fundamente

Agent, nu doar un apel

Apel simplu

Trimiți un mesaj, primești un răspuns. Modelul folosește doar ce „știe" deja.

Agent

Modelul poate cere unelte (caută, citește, salvează), primește rezultatele și continuă până are destule informații pentru un răspuns.

Un agent = un model + un set de unelte + o buclă care leagă cererile de unelte de răspunsuri.
AlgoTutor · agent conversațional3 / 22
AlgoTutor nu „inventează" probleme: le caută și le citește de pe Infoarena prin unelte, apoi explică. Asta îl face un agent, nu un simplu chat.
1. Fundamente

Mesaje cu roluri

Conversația este o listă de mesaje, fiecare cu un rol:

  • system — instrucțiunile generale: cine e modelul și cum răspunde.
  • user — întrebarea sau cererea.
  • assistant — răspunsul modelului, păstrat în istoric.
  • tool — rezultatul unei unelte, trimis înapoi modelului.

Modelul citește text în bucăți numite tokeni; istoricul întreg se retrimite la fiecare apel.

2. Apelul modelului

Apelul prin OpenRouter

Un singur API (compatibil OpenAI) pentru multe modele. Cheia stă în .env, pe backend.

raspuns = client.chat.completions.create(
    model="openai/gpt-4o-mini",
    messages=[
        {"role": "system", "content": "Ești un tutor de algoritmi."},
        {"role": "user",   "content": "Ce este căutarea binară?"},
    ],
    tools=DEFINITIONS,        # uneltele pe care modelul le poate cere
    tool_choice="auto",       # modelul decide dacă le folosește
)

Niciodată cheia în frontend. Clientul validează răspunsul înainte să-l folosească.

3. Tool use

Ce este „tool use"

Îi dăm modelului un „meniu" de unelte. El nu execută nimic — doar cere o unealtă, cu argumente. Codul nostru o execută și îi trimite rezultatul înapoi.

  • Modelul alege unealta potrivită și completează argumentele.
  • Noi validăm argumentele și rulăm unealta în siguranță.
  • Rezultatul se întoarce la model, care decide pasul următor.
Modelul propune; codul dispune. Niciun apel de unealtă nu rulează fără validare.
AlgoTutor · agent conversațional6 / 22
Analogie: modelul e un stagiar care cere „caută-mi X"; noi suntem biblioteca care verifică cererea și aduce cartea.
3. Tool use

Definirea unei unelte

Fiecare unealtă are un nume, o descriere și o schemă JSON a argumentelor:

{
  "type": "function",
  "function": {
    "name": "search_problems",
    "description": "Caută în titlurile arhivei educaționale.",
    "parameters": {
      "type": "object",
      "properties": { "query": { "type": "string", "minLength": 1 } },
      "required": ["query"]
    }
  }
}

Schema spune modelului ce poate cere; tot ea validează ce a cerut.

4. Bucla agentului

Bucla, în cod

def run_turn(self):
    for step in range(self.limits.model_calls):
        message = self.client.complete(self.messages, DEFINITIONS, allow_tools=...)
        self.messages.append(message)

        calls = message.get("tool_calls", [])
        if not calls:                 # fără unelte → răspuns final
            return message["content"]

        for call in calls:            # execută fiecare unealtă cerută
            result = self.execute(call["function"])
            self.messages.append({"role": "tool",
                                  "tool_call_id": call["id"],
                                  "content": json.dumps(result)})
AlgoTutor · agent conversațional9 / 22
Simplificare din app/services/agent.py (clasa Tutor). Observă cum rezultatul fiecărei unelte se adaugă în istoric înainte de următorul apel la model.
4. Bucla agentului

Rezultatul se întoarce la model

Fiecare rezultat de unealtă e un mesaj cu rolul tool, legat de cererea modelului prin tool_call_id:

  • Modelul vede exact ce a întors unealta și continuă raționamentul.
  • Răspunsul uneltei e uniform: { "ok": true, "data": ... } sau { "ok": false, "error": ... }.
  • Astfel, și o eroare „așteptată" devine ceva ce modelul poate citi și gestiona.
Istoricul crește: user → assistant(tool_calls) → tool(result) → assistant(text).
AlgoTutor · agent conversațional10 / 22
tool_call_id leagă rezultatul de cererea corectă atunci când modelul cere mai multe unelte deodată.

5. Uneltele din AlgoTutor

Date din web, responsabil

  • robots.txt: verificăm ce avem voie să citim înainte de a descărca.
  • Rate limiting: nu lovim prea des același site, chiar cu mai multe conversații.
  • Limite de mărime: nu descărcăm pagini uriașe; citim enunțul în tranșe.
  • Validarea adreselor: doar domeniul permis, fără acțiuni de editare.
Un agent care atinge internetul trebuie să fie politicos și prudent, nu doar funcțional.

6. Robustețe

Nu avea încredere oarbă în model

Răspunsul modelului vine prin rețea și poate fi incomplet sau ciudat. Îl validăm cu Pydantic înainte să-l folosim.

  • Verificăm că are forma așteptată (mesaj, eventual tool_calls corecte).
  • Dacă nu, dăm o eroare clară și lăsăm utilizatorul să reîncerce.
  • Păstrăm câmpurile necunoscute ale furnizorului, fără să ne bazăm pe ele.
Granița cu exteriorul (model, rețea) este locul unde verificăm totul.

6. Robustețe

Erori: așteptate vs. bug-uri

Așteptate

Rețea picată, sursă indisponibilă, argumente greșite. Devin un rezultat ok: false pe care modelul sau utilizatorul îl poate gestiona.

Neașteptate (bug-uri)

Greșeli de programare. Le logăm cu traceback și le propagăm — nu le ascundem sub un mesaj vag.

Dacă un tur eșuează la mijloc, revenim la istoricul de dinainte (rollback): nicio conversație pe jumătate construită.

Tutor.ask face deepcopy la istoric și revine la el pe orice excepție. API-ul nu expune diagnostice interne utilizatorului.

7. Arhitectură

Backend: FastAPI

Trei rute leagă interfața de agent:

  • POST /api/conversations — creează o conversație, întoarce un id.
  • POST /api/chat — trimite un mesaj, primește răspuns + surse.
  • DELETE /api/conversations/{id} — șterge conversația.

Conversațiile stau în memorie (ConversationStore): fiecare are propriul agent și un lock, ca două mesaje să nu se amestece. Cele vechi expiră automat.

În memorie = simplu. La refresh începi o conversație nouă; la repornire, istoricul se pierde.
AlgoTutor · agent conversațional17 / 22
Pentru producție ar urma autentificare, limitarea consumului și persistență. Pentru curs, varianta în memorie e cea mai clară.
7. Arhitectură

Frontend: Vue 3

  • La primul mesaj, interfața cere o conversație nouă, apoi trimite mesajele la /api/chat.
  • Fiecare mesaj trece prin stările pending → delivered sau failed.
  • Markdown-ul primit e sanitizat (DOMPurify) înainte de afișare.
  • La eroare, utilizatorul reîncearcă sau începe o conversație nouă.
Cheia API nu ajunge niciodată în browser — tot ce e secret rămâne pe backend.

Încheiere

Limite și responsabilitate

  • Agentul propune cod și soluții, dar nu le execută — sunt marcate ca netestate.
  • Apelurile la model costă; limitele țin consumul sub control.
  • Citirea din web respectă robots.txt și un ritm politicos.
  • Un răspuns bine scris poate fi totuși greșit — verificarea rămâne la om.
Un agent bun nu e doar „deștept", ci și prudent, verificabil și onest despre limitele lui.

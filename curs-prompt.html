1. Fundamentals

What is a prompt

A prompt is the instruction you give the model. Same model, different prompts → different results.

Vague

„Write about Paris." → generic, unpredictable answer.

Good

„Write 3 sentences about Paris for a 5th-grade student, in simple English." → useful and controlled.

Prompt engineering = the art of being explicit: what you want, for whom, in what form.
Prompt Engineering3 / 22
Key idea: control comes from specificity. A good prompt reduces ambiguity.
1. Fundamentals

Messages with roles

A conversation is a list of messages, each with a role:

system

General instructions: who the model is and how it answers.

user

The concrete question or request.

assistant

The model's answer, kept in history.

tool

The result of a tool (for agents).

The „system" prompt is where you put the stable rules of the conversation.

Prompt Engineering4 / 22
system = rules; user = request; assistant = answer. The model has no memory of its own — history is resent each time.

2. Framework

Why one prompt works on any model

CROFC is plain language, not model syntax. Every chat model takes the same thing: messages with roles + clear instructions.

ChatGPTClaudeGeminiLlamalocal

No special tokens

You write natural language, not model-specific markup.

Same roles everywhere

system / user / assistant are a shared standard.

Structure, not tricks

Context, goal, format, constraints help any model.

Switching models? A CROFC prompt usually works as-is — maybe a small tweak to tone or length.

In practice · examples

Example — compare two products

Which phone fits my needs?

A buyer choosing between two phones on a budget.

Context: I want a phone for WhatsApp, photos and video calls. Budget: 1500 lei. Role: act as an impartial tech advisor. Objective: recommend between Samsung A26 and A36 for my needs. Format: a short table — price, battery, camera, verdict. Constraints: max 150 words, no jargon.

The same CROFC shape, filled for a real decision. Inspired by RO.1M.AI.

In practice · examples

Example — a weekend in Sibiu

Plan two days with the family

A parent planning a short trip.

Context: a weekend (Sat–Sun) in Sibiu with two kids (6 and 9). Role: act as a local guide. Objective: a 2-day plan of things to do. Format: a schedule per day, 3–4 activities each, with rough times. Constraints: family-friendly, mostly walking distance, include one rainy-day option.

Change the Context and Constraints, reuse the structure.

Apply for a junior role

A student applying for a first job.

In practice · examples

Example — live iPhone prices (eMAG)

Fetch today's prices into a table

Live data — needs an AI with web access (an agent).

Context: I'm comparing iPhone models on eMAG.ro. Role: act as a price researcher with web access. Objective: find today's price for iPhone 15, 15 Pro, 16 and 16 Pro. Format: a table — model, price (RON), seller, link. Constraints: only eMAG.ro; add the date; do not invent prices; if a model is missing, say so.

Plain chat can't fetch live prices — this needs tools/browsing, i.e. an agent (see the agents course).

Example — a synthetic CV dataset

Generate fake-but-realistic test data

Synthetic data — works on any model, no internet.

Context: I need test data for a CV-parsing tool. No real people. Role: act as a synthetic data generator. Objective: create 5 realistic but fictional CVs for junior developers. Format: a JSON array; each item has name, email, skills[], experience[], education. Constraints: invented data only (GDPR-safe), diverse profiles, Romanian context.

Great for testing, demos and training — without touching real personal data.

2. Framework

Vague vs. structured

Vague

„Write me an offer for a client."

CROFC

Context + Role + Objective + Format + Constraints → ready to use.

C — Context      I'm preparing an offer for a new, non-technical client.
R — Role         Act as a business consultant.
O — Objective    Write the offer based on my services.
F — Format       Answer in 5 clear bullet points.
C — Constraints  Max 120 words, professional tone, no jargon.

3. Techniques

Zero-shot vs. few-shot

With few-shot you give a few input → output examples. The model imitates the pattern.

Classify the sentiment (positive / negative):

Text: „Fast delivery, I'm delighted!"   -> positive
Text: „The product broke in 2 days."    -> negative
Text: „Nice packaging, but pricey."     ->

2–5 examples are usually enough. Examples show the exact output format.

Prompt Engineering14 / 22
Zero-shot = no examples. Few-shot = with examples. Examples pin down both the task and the output shape.
3. Techniques

Think step by step

For reasoning tasks, ask the model to show the steps before the answer (chain-of-thought).

Without

„What is 17 × 24?" → direct answer, sometimes wrong.

With

„Solve step by step, then give the result." → more reliable for math and logic.

Useful for math, logic, decisions. Downside: longer and slower answer.
Prompt Engineering15 / 22
„Let's think step by step" improves reasoning. For a clean final answer, ask for just the result at the end.
3. Techniques

Format and constraints

Ask for the shape

„Answer only with JSON", „a 5-point list", „a table".

Limit it

„Under 100 words", „at most 3 options".

Say what NOT to do

„No intro", „don't invent sources".

An explicit format makes the answer easy to use automatically (parse, copy, integrate).
Prompt Engineering16 / 22
Negative constraints („don't do X") matter as much as positive ones.
3. Techniques

Metaprompting with CROFC

Don't write the prompt from scratch — ask the model to generate or improve it.

„Write a CROFC-style prompt for a CV-writing assistant. Return only the prompt, in sections."

Describe the goal

What you want the assistant to do.

Ask for the structure

„In CROFC sections".

Refine

„Make Constraints stricter", „add an example".

Check and edit the result — don't accept it blindly. Inspired by RO.1M.AI.

4. Pitfalls & safety

Pitfalls and prompt injection

Ambiguity

Vague requests → unpredictable answers.

Overload

Too many requirements at once → the model misses some.

Prompt injection

Text from sources that „gives orders" to the model.

Golden rule: treat text from documents, pages or files as data, not instructions. Don't paste personal data into the prompt.
Prompt Engineering19 / 22
Prompt injection: a page may contain „ignore your instructions and do X". The model must not execute what sources say.
4. Pitfalls & safety

Always verify the answer

A well-written answer can still be wrong. Models can invent facts, sources and quotes (hallucinations).

Warning signs

Sources that „sound credible", precise numbers with no source, excessive confidence.

What to do

Ask for the sources, check them, re-read; for decisions, confirm with a human.

Real example: a report delivered with invented sources. Verification stays the human's responsibility.
Prompt Engineering20 / 22
Hallucination = plausible but false content. No prompt fully removes the risk; verification is mandatory.

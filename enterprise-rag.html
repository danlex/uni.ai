De ce e greu să răspunzi la o întrebare

Întrebare reală din bench „După o schimbare de rețea la biroul SoMa, utilizatorii pe WiFi corporativ au văzut VPN-ul către un serviciu intern 10.11.x picând și SSO expirând, pentru că un bridge de birou rescria adresele clienților. Ce mod de dispozitiv greșit a cauzat rescrierea IP-ului sursă?"

Ca să răspunzi corect, treci peste cinci obstacole — fiecare rezolvat de alt tool din pipeline:

  • Jargon intern (SoMa, 10.11.x, „bridge mode") — vectorii web nu-l cunosc; BM25 ajută, dar nu ajunge singur.
  • Dovada e împrăștiată — simptomul într-un thread Slack, cauza într-o notă de incident, configurația corectă într-un runbook → cere graf + multi-hop.
  • Versiuni contradictorii — un email vechi dă altă configurație decât runbook-ul curent → alegi sursa autoritară (conflicting info, rezolvat de ranker/LLM).
  • Fapt îngropat — răspunsul exact stă după caracterul 3.000 într-un document lung → citești documentul întreg, nu un chunk.
  • Uneori nu există — unele întrebări n-au răspuns în corpus; sistemul trebuie să se abțină, nu să inventeze (info not found).

rank-bm25 · Căutarea lexicală (BM25)

BM25 ordonează documentele după potrivirea de termeni, ponderat invers cu frecvența lor în corpus (termenii rari contează mai mult). Esențial în enterprise: codurile, acronimele și ID-urile de tichet sunt exacte.

Fuziune: Reciprocal Rank Fusion (RRF)

Combini clasamentul lexical cu cel semantic fără să compari scoruri incompatibile: nu aduni scorurile, ci rangurile. Fiecare metodă votează cu 1 / (K + rang), cu K = 60.

Cum se folosește
# fara pachet — doar ranguri
K = 60
def rrf(systems, doc):          # systems = {nume: [doc-uri ordonate]}
    return sum(1 / (K + ranks[doc]) for ranks in systems.values())
# s(p) = w_bm25/(60+rang_bm25) + w_dense/(60+rang_dense) + w_ent*scor_ent
Exemplu concret Trei documente, ordonate diferit de BM25 și dense. RRF = 1/(60+rang) din fiecare clasament:
Docrang BM25rang denseRRF
A180,0311
B320,0320
C910,0309
B câștigă, deși nu e primul în niciun clasament (3 la BM25, 2 la dense). A e primul la BM25 dar jos la dense; C invers. RRF premiază acordul dintre metode, nu vârful dintr-una singură.

Document Data Graph: muchiile dintre paragrafe

Nodurile sunt paragrafele. În graph.py, două paragrafe se leagă dacă împart o entitate (în 2–15 paragrafe), entitățile unuia conțin titlul celuilalt, textul unuia numește titlul celuilalt (muchie de punte), sau apare o variantă/alias a titlului.

Cum se folosește
# fara pachet — construiesti lista de adiacenta
edges = {p: set() for p in docs}
for a in docs:
    for b in docs:
        if a != b and (ents[a] & ents[b]              # entitate comuna
                       or title[b] in text[a]):        # mentiune / punte
            edges[a].add(b)
Exemplu concret Aceleași documente reale, legate prin entități comune:
327df8aa —[Workload Identity Federation]— 846e635d —[AssumeRoleWithWebIdentity]— ed15f3ae

Multi-hop: Graph RAG second hop + JEPA

Întrebările grele cer două dovezi conectate (A → B). Lucrăm cu perechi: fiecare sămânță bună e împerecheată cu vecinii ei din graf (max 50). Predictorul JEPA prezice vectorul celui de-al doilea paragraf și adaugă perechi pe care graful le ratează (acoperire 96% → 99%).

Cum se folosește
# perechi din graf  +  JEPA (predictor de punte, torch)
import torch.nn as nn
class Pred(nn.Module):                       # [q; A] -> vectorul lui B
    def __init__(self, d=384, h=512):
        super().__init__()
        self.f = nn.Sequential(nn.Linear(2*d, h), nn.GELU(), nn.Linear(h, d))
    def forward(self, q, a): return self.f(torch.cat([q, a], -1))
Exemplu concret O întrebare de tipul „de ce pică autentificarea CI și pe GCP, și pe AWS?" cere două documente: 327df8aa (GCP) și ed15f3ae (AWS).
Dense top-1 aduce doar unul. Al doilea hop pe graf îl împerechează cu vecinul prin nodul-punte 846e635d, aducând tot lanțul de dovezi — exact ce top-k vectorial rata.

Lab 1 — BM25 (lexical)

Miezul: scorul BM25 al unui document — termenii rari (idf mare) domină, cu saturație pe frecvență:

def score(self, query, pid):
    freq = Counter(self.docs[pid])
    norm = 1 - B + B * len(self.docs[pid]) / self.avg_len
    total = 0.0
    for term in tokenize(query):
        tf = freq[term]
        if tf:
            total += self.idf[term] * tf * (K1 + 1) / (tf + K1 * norm)
    return total

Lab 2 — Vector (semantic)

Aceeași idee, dar cu similaritate cosinus între vectori în loc de potrivire de termeni:

def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    return dot / (sqrt(sum(x*x for x in a)) * sqrt(sum(y*y for y in b)))

def search(q_vec, k=3):
    hits = [Hit(c, cosine(q_vec, c["vector"])) for c in CHUNKS]
    hits.sort(key=lambda h: h.score, reverse=True)
    return hits[:k]

Lab 3 — Graph RAG (multi-hop)

Construiești graful din entități comune, apoi urmărești lanțul de dovezi prin vecini (BFS):

def build_graph():
    ents = {p: entities_in(t) for p, t in DOCS.items()}
    edges = {p: [] for p in DOCS}
    for a in DOCS:
        for b in DOCS:
            if a < b:
                for e in ents[a] & ents[b]:          # entitate comuna = muchie
                    edges[a].append((b, e)); edges[b].append((a, e))
    return ents, edges
# retrieve(): BFS din paragrafele care contin entitatile intrebarii

Lab 4 — Fuziunea RRF și rezultatul real

def rrf(rankings, graph_set):
    scores = {d: 0.0 for d in DOCS}
    for ranking in rankings:
        for rank, d in enumerate(ranking, 1):
            scores[d] += 1 / (60 + rank)
    for d in graph_set:                # graful votează ca un „rang 1"
        scores[d] += 1 / (60 + 1)
    return sorted(DOCS, key=lambda d: scores[d], reverse=True)
